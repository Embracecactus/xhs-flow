# Artifact Flow｜同一firmware的工程对象流

配套：[Visual Treatment](visual-treatment.md)、[Shot List](shot-list.md)。

**所有文件名为拟交付命名，不表示文件已生成。当前仅有本导演设计文档。** 取得真实工程后沿用实际文件名，不为视觉效果重命名原素材。

## 1. 主链与支链

```text
A0 原始固件构建包 / firmware.bin
 ├─→ A1 分析证据 / analysis_report.md + memory_map.json
 │    └─→ A2 可复现虚拟环境 / environment_manifest.json
 └───────────────┴─→ A3 原版本执行记录 / trace.log + run_manifest.json
                       ↓
                     A4 问题与定位证据 / issue_report.md
                       ↓
                     A5 有依据的修订 / fix.patch + change_record.md
                       ↓
                     A6 修订固件构建包 / firmware_v2.bin
                       ↓ 与同一A2、同一检查标准组合
                     A7 修订版执行记录 / trace_v2.log
                       ↓ 结合A3、A4、A5、A6核对差异
                     A8 有限验证报告 / validation_report.md
                       ↓
                     A9 实机待验证清单 / hardware_checklist.md
```

A0与A6是同一工程的不同构建，不是同一个哈希。其他产物是分析、环境、观察与结论，不能互相替代。

## 2. Artifact定义

|ID / 状态|输入|产物及最少内容|准入条件|不能据此宣称|
|---|---|---|---|---|
|A0｜原始镜像已识别|授权工程、构建说明、真实目标身份|原始bin、配套ELF、链接map、linker、构建身份；实际生成了哪些就记录哪些|来源、目标、配置、工具链与文件哈希可追溯；原素材只读|存在bin就能在任意QEMU机器运行|
|A1｜布局与依赖已分析|A0及相关源码|`analysis_report.md`；`memory_map.json`含区域来源、装载段、入口/向量、栈与设备依赖|每项事实引用对应文件/符号；未知项显式保留|分析报告已经证明程序能启动|
|A2｜环境与规则已锁定|A1、固定QEMU实现与能力范围|`environment_manifest.json`含QEMU身份、命令、机器、装载方式、后端、观察方式、超时与判定规则|机器/镜像匹配，支持与未支持项可区分；只配置已有模型时如实说明|已经构建完整虚拟芯片或完成OS启动|
|A3｜原版行为已记录|A0+A2|`trace.log`、原始stdout/stderr、实际状态观察及`run_manifest.json`，标明执行点与输出是否出现|同一运行身份；记录实际命令和镜像哈希；trace内容类型明确|无输出必然说明缺门控；PC变化等于启动通过|
|A4｜问题有证据与解释|A3、A1、A2、设备源码|`issue_report.md`含现象、候选原因、支持/反证、其他解释及验证方式|“发现现象”与“确认原因”分开；证据不足标为未确定|候选Clock gate missing已经是根因|
|A5｜改动有依据|已支持的A4与源码|`fix.patch`和`change_record.md`，列明改哪一项、为什么、预期改变与不变条件|保存旧版本；实际差异可复核；额外环境变化披露|源码改完即修复成功|
|A6｜修订镜像已重建|A5、可复现构建|`firmware_v2.bin`及配套ELF/map、构建记录、新哈希和父版本关联|新产物确由修订构建；不覆盖A0；核对入口与布局仍匹配A2|新镜像的成功属于原镜像|
|A7｜修订行为已记录|A6+A2，同一检查标准|`trace_v2.log`、原始输出、状态观察、新运行身份|从复位重新运行；按同条件核对，不拼接两轮日志|打印Firmware started即所有测试通过|
|A8｜有限结果已核验|A3–A7及预定标准|`validation_report.md`含版本对应、入口/状态、输出来源、前后差异、结果与未覆盖项|实际证据支持结果；失败/未完成项保留；归因不过界|完整产品Boot、全芯片或实机验收通过|
|A9｜硬件工作仍待完成|A8、真实目标信息|`hardware_checklist.md`列明待实机入口、接口与测量；没有板时状态保持待执行|与目标型号/版本相符；不把实板照片当测试证据|已刷机、实测或获得实体结果|

## 3. 身份与连续性规则

每项产物应能引用：工程身份、父产物、源版本、构建配置、文件哈希、工具/QEMU版本、运行身份、证据路径与状态。当前未取得的值不填示例值冒充真实数据。

执行使用ELF时，运行记录必须绑定其哈希，并记录其与主bin的构建关系。不能只标一个bin文件名，实际运行另一份不相关ELF。

`trace.log`具体可能是CPU trace、设备事件或调试采样；实施时分别说明，不把几种记录混成“全系统真实trace”。终端输出与trace可关联，但不是同一种证据。

`memory_map.json`是从ELF/map/linker及模型配置提取的派生产物，注明每个区间来源；不是AI猜出的地址表。

目录版本、镜像哈希、运行身份必须在失败与复跑段保持可回查，不必全部占据画面。

## 4. 候选UART案例的依赖

若采用“UART沉默→门控遗漏”案例：

1. 确认程序是否到达发送路径；若未到，不能从UART开始归因。
2. 检查TX使能、就绪、时钟选择/门控、合法访问及后端连接。
3. 用对应模型源码与运行状态支持判断；停止时钟下写入可能被忽略，不能画成必然入队后等待。
4. 单项改动与复跑对照支持原因，不能同时换串口后端、镜像和模型策略后只归因一个变量。
5. 用独立有效的时间来源进行失败判定；不能用同样被关闭的UART功能时钟提供超时依据。

若实际原因不成立，A4继续定位，镜头05–08相应调整。没有证据时不预生成成功报告。

## 5. 任务标识与产物

分析任务关联A1；环境任务关联A2；运行任务关联A3/A7；定位任务关联A4；修订任务关联A5/A6；核验任务关联A8/A9。

标识只标当前职责与真实状态。当前默认单Agent，不把这些职责数量转成独立Agent数量，也不造并行完成记录。
