# Engineering / Visual Treatment｜《没插开发板，固件为什么还能跑？》

**当前方向：工业科技纪录片＋AI工程助手演示。**

**主角：同一份真实固件工程及其启动验证过程。**

AI以工程任务、工具动作与证据产物存在，不是人物。禁止卡通、动漫、虚构世界、真人剧情及拟人设备。本方案取代人物故事与“只有一次顺利输出”的旧主线；旧文档和样段保留，不移用其审核。

## 1. 影片承诺

开发板未到，验证工作也能先推进一部分。影片展示的不是QEMU教程，而是一次工程工作如何从不确定，走到有证据的有限结论。

**任务 → 分析 → 配置环境 → 运行 → 发现问题 → 定位 → 修改 → 重建复跑 → 有限验证 → 等待实机。**

“UART silent / Clock gate missing / Firmware started”是用户提出的候选事件，不是已发生的事实。本次只做分析与方案，未运行或修改固件，未生成画面。

## 2. 世界与对象：真实工作区＋软件机制可视化

不再建设一个世界观城市。所有空间都由工程对象及其关系产生：

- **现实桌面：** 目标板缺席，宿主与工作材料存在；不出镜操作者。
- **真实工程界面：** 实际源码、构建产物、配置、终端、差异与任务记录。没有素材时标为待取得，不用仿制UI充当录屏。
- **3D模型视图：** 把该环境的CPU状态、内存映射和设备响应空间化。它是软件模型的示意，不是BK7258实体硅片内部、实际版图或物理信号仿真。

片中模型必须有“模型示意”身份；真实终端录屏与机制CG有清楚的视觉区分。CG不替代运行证据，真实日志也不自动证明实机能力。

当前工程基线是已研究的固定`qemu-bk7258`诊断环境，不能把工业相机板、其他MCU板或RTEMS启动结果随意混入这一版本。

## 3. AI工程任务怎样被看见

五类任务标识保留用户希望表达的工程分工，但不设计形体、脸、性格或台词：

|任务标识|实际输入|应产生的证据或判断|关联画面|
|---|---|---|---|
|Boot分析|ELF程序头、向量、linker、启动代码、装载配置|装载地址、初始SP/复位入口与诊断模式相符；注明绕过路线|真实文件位置接到装载/入口模型局部|
|Memory分析|链接map、装载映射、初始化实现、状态采样|代码、RAM、栈范围与实际访问一致；必要初始化检查|真实区间与对应存储状态变化|
|CPU状态|同次运行的调试/trace记录|到达哪个位置、是否异常或等待；不把PC在动等同启动通过|PC停点接到实际指令/源码位置|
|外设模型分析|设备源码、配置访问、时钟与TX状态|模型支持哪些条件、哪些依赖未成立；与固件操作对照|MMIO访问定位UART条件与接纳状态|
|日志分析|同次命令、退出/超时情况、stdout/stderr与后端配置|输出来自哪里；失败与复跑的具体差异|日志行、事件定位与验证结果|

**标识形式：** 小型文字标签、定位线、任务状态和证据入口。只在相关对象被处理时出现，完成后留下产物；不铺满五张“Agent卡片”当动态PPT。

状态由记录驱动：待处理、分析中、待验证、阻塞、完成。没有记录，不播放“完成”；推断先标为候选原因。

当前环境默认单Agent：五类标识是职责视图，不是五个独立Agent已并行执行。若后续确实采用多Agent，须有真实子任务、输入、执行与合并记录；不为拍团队表演临时搭建第二套Agent平台。

## 4. 六阶段视觉推进

### 第一阶段｜任务与分析

**开场：** 实际桌面上的空目标位。字幕采用用户给定的任务前提：

> 开发板还没到，但是固件验证不能停。

随后进入同一工程的实际材料：源码、ELF、链接map、linker script，以及确实生成的`firmware.bin`。名称使用真实文件名，不为镜头强行重命名。

摄影从文件整体进入某个真实位置：向量、可装载段或栈范围。任务标识出现，相关位置被定位，分析产物形成。

ELF、map和linker分别承担镜像内容、链接结果与布局约束，不画成四个互相替代的文件。ELF与bin若同时出现，核对其构建对应关系；raw bin不是看见文件名就知道入口。

**推进结果：** 明确这份固件期待什么环境、能采用什么入口、哪些条件不匹配。不能从“分析完成”直接跳到“启动完成”。

### 第二阶段｜配置并建立虚拟硬件环境

真实QEMU启动命令与固定版本先建立来源，再切入工业CG模型。

CPU、RAM、UART按该机器配置形成结构，Timer只在真实任务使用时加入——例如作为独立的诊断超时依据。不为凑四个设备标签，让没有参与验证的模块运转。

模型建立不是“AI现场创造了完整芯片”。若只是选择已有机器和设备模型，就表现为配置、实例化、连接；只有真的修改了模型，才展示对应源码差异与模型测试。

**摄影：** 总景交代结构，局部显示映射与连接；模型不凭空冒出实体PCB或封装引脚。

**推进结果：** 出现一套具体、有限、匹配的运行条件，而不是整颗SoC能力宣告。

### 第三阶段｜运行并观察

显示这次实际执行的终端与记录。RTEMS boot、I2C init、UART output仅在相应固件确实执行并取得日志时使用；当前基线不能提前承诺完整RTEMS或产品启动。

CG与记录同步：

- PC位置对应实际观测的执行点。
- Memory变化对应真实初始化或访问结果。
- MMIO定位对应真实地址、宽度、负载与设备响应。

使用暂停采样时说明它是状态观察，不把剪辑节奏当指令频率，也不假装逐周期录制。终端节选可缩短观看时间，但保留运行身份，不拼接不同运行制造连续成功。

**推进结果：** 程序具体走到了哪里，以及约定结果是否出现。画面能表达“CPU到达应用”和“UART仍无输出”同时成立。

### 第四阶段｜问题与定位——全片重点

如果实际复现UART沉默，先表现缺失结果，随后沿证据缩小范围。不要首次静音就跳出`Clock gate missing`。

候选解释包括入口未到、异常/等待、TX未启用、功能时钟无效、后端连接错误、访问模型不支持等。

任务标识沿实际记录定位：

1. 确认执行是否到达发送路径。
2. 对照初始化访问与UART就绪状态。
3. 核对时钟选择、分频与门控，以及宿主输出后端。
4. 用可复现的观察或对照实验支持原因，排除其他解释。

只有证据支持时，才把候选原因升级为`Clock gate missing`。固定模型文档已有“停止时钟时TX不就绪、停止时写入被忽略”的机制依据，但这不是本次固件遗漏门控的运行证据。

**摄影：** 由终端的沉默回到实际执行点，再进入门控/就绪状态局部。不是在一张电路图上随机搜寻发光点。

**推进结果：** 一个宽泛现象变成明确的、可验证的原因。AI价值体现在这一变化，而非聊天宣告。

### 第五阶段｜修复、重建与复跑

展示真实源码diff及其理由，重新构建，记录新镜像身份，再从复位启动新版本。

失败与修订版本用相同机器配置、后端和判定标准对比。若其他条件也改了，明确披露，不制造单一归因。

若修的是模型而不是固件，必须如实称为模型修复，并补模型测试；不能改设备返回值让程序“过关”，再包装成固件修复。

终端输出只取实际固件内容。`Firmware started`不能由后期打上去；程序无条件打印一句话也不是充分的启动验证。

**高潮镜头：** 关联MMIO访问被接纳、TX推进、宿主字符后端输出，终端终于出现对应结果。保留短暂停顿，让前一轮的沉默与本轮回应形成对照。

**推进结果：** 获得入口、状态检查和UART来源共同支持的有限结论。不出现整芯片绿色通过或虚构性能数据。

### 第六阶段｜回到真实目标，留下下一项工作

不以虚拟模型为最后一镜，回到真实桌面与目标硬件任务。

若有同一型号/版本的授权实板素材，可拍板卡微距，但明确“待实机验证”，不以板子出现暗示已经刷机或验收。若目标板仍未到，就回到开场真实空位；不生成AI板照充当实物。

验证记录里的软件路径已有结果，硬件项目仍待完成。字幕：

> 虚拟环境不能替代硬件，但可以让软件提前面对问题。

结尾回报是软件工作已经前进，而不是等待的目标被模拟器取消。

## 5. 工业CG完成度

### 场景与摄影

同一模型贯穿，不按阶段更换不同科技背景。总览、微距、代码位置与终端之间有可追踪的空间/证据关系。

施工与诊断段稳住相机，让状态变化取得注意力；只有需要定位或进入问题时才改变尺度。可用斜俯视、窄景深微距和产品式侧光，但关键状态不能被虚化遮住。

### 材质与光影

石墨灰、陶瓷白、缎面金属为结构基调，细倒角、受控高光与接触阴影提供可信体积。透明截面只用于暴露关系，不泛滥成全息科幻。

冷色用于当前访问，低饱和暖色用于候选阻塞点；已验证状态保持稳定，不满场霓虹。强调色不代替具体证据。

### 细节密度

细节来自真实文件身份、映射区间、指令位置、寄存器条件和前后差异。未知内容不补乱码、不写假日志、不造热图、波形或Agent用量。

软件事务不是铜线电流。动画速度、模型尺寸、可见槽数不声明真实频率、容量或物理时序。

### 动画与声音

Blender制作原创模型与摄影；真实界面/日志取自可追溯录屏或记录，合成层负责定位与节选。动画状态由同一事件/状态记录驱动，不凭字幕时点随机闪灯。

少量原创工程事件提示可强化时序，不用卡通拟音或人物对白。声音不伪装为真实芯片、引脚或设备测量。

## 6. 开拍前必须取得的证据包

当前在`firmware-universe`、`workspace/douyin`与已用研究缓存的定向检查中，没有找到匹配目标ELF、固件链接map、linker script或`firmware.bin`。搜索到的`.js.map`是前端source map，不是固件链接产物；此结论不扩大到整个WSL或其他项目。

|证据|目前状态|用途|
|---|---|---|
|真实工程/授权来源、构建说明、目标型号与版本|待取得|决定拍的是产品工程还是诊断实验|
|匹配ELF、链接map、linker及确实生成的bin|待取得/构建|核对布局、入口、初始化与镜像身份|
|QEMU精确提交、实际可用构建、命令与能力范围|已有固定提交研究；本次执行待核实|避免套用其他机器或最新版本结果|
|失败运行的入口/状态、stdout/stderr、超时和设备记录|未执行|确定真实问题，而不是预设根因|
|原因验证、源码diff、重建身份、同条件复跑|未执行|支持修复归因与有限结果|
|授权、型号匹配的实板素材与实机记录|未取得|区分真实目标呈现与硬件验收|
|AI任务/工具记录|本次只有研究记录；固件任务尚未执行|不伪造独立Agent与自动修复能力|

若最终采用人为注入遗漏的原创诊断测试，必须明确标为**受控故障实验**，不能称为某个真实产品事故。不因剧情需要而伪造问题；若实际原因不同，故事跟随真实原因调整。

本诊断基线仍绕过ROM/Bootloader，不能升级成完整Boot、安全启动、全外设或实机验收。新增OS/外设/真实启动模式需要另外核对，不继承旧机制审核。
